## Token movement audit — 2026-11-27

The prior `token:move` handler read the token, role and scene outside the write. The update predicate used only the token ID and version. Membership removal, demotion and scene changes could commit between authorization and movement without changing the token version. The handshake and room check did not synchronize a write with logout. The conflict path read state and permissions separately. The REST group resolved session, scene and role before opening its transaction, acquired token locks without an explicit order, and allowed positional patches on locked tokens. The old token-copy paths also acquired scene and token locks in different orders.

The shared [movement transaction](../architecture/ARCHITECTURE.md#token-movement-transaction) synchronizes authorization with its writers. Reassignment and multi-scene updates use compatible locks. Group validation precedes all writes. Movement and group events select their audience after commit and filter live sessions, roles and visibility. Rejections expose only permitted conflict projections.

All 23 movement scenarios passed against isolated PostgreSQL 16.15 with real HTTP and Socket.IO clients. The tests inspect `pg_blocking_pids` to order competing requests, then check persisted rows, audit records and packets. They cover both orders of membership removal versus movement, role demotion, owner reassignment, scene archive, token locking, session logout, overlapping groups, hidden conflict details, multiple sockets and reconnect. A target-scoped PostgreSQL test trigger rejects audit insertion after the group token writes. The failure preserved both prior rows and published no token event.

## Object lifecycle audit — 2026-11-27

At baseline `4fd8fb1`, the group endpoint resolved session, scene and campaign role before opening its write transaction. PostgreSQL locked the object rows only. The joined layer's lock and visibility flags could change without advancing the object version. The point-delete path also published before its separate audit insert. Player point deletion required authorship and a freehand object, but lacked active-scene and visibility checks. These are gaps in the baseline predicates and transaction boundaries. The regressions verify the corrected behavior on isolated test fixtures.

The [object lifecycle transaction](../architecture/ARCHITECTURE.md#scene-object-lifecycle-transaction) serializes the relevant access checks with role and session changes, layer edits and removal, object moves and scene archive. The resulting audit and object changes share one commit. All 28 PostgreSQL scenarios passed locally, including a forced audit failure after the batch SQL write. Controlled post-commit tests held publication before audience authorization, then hid a layer or demoted a member with two open sockets. The newly unauthorized sessions received no private restore. Reconnect verified the committed revision from a fresh snapshot.

At this checkpoint the per-recipient checks covered lifecycle and token movement. The following checkpoint extends them to ordinary scene content. Socket.IO packets already queued before a later permission change cannot be recalled. The deployment has no durable event replay.

## Secure scene-content delivery

The [matrix](REALTIME_EVENT_MATRIX.md) inventories all 24 outbound event names. At baseline `7fd3d6be`, ordinary object/layer events trusted rooms and earlier entity state when enqueuing packets. Create also checked actor and layer before a separate write and audit. Creation now locks the same authorization and scene rows as edits. Copy checks source and destination layers under locks. A copy from a private source retains private object visibility, including when placed on a public layer.

Object and layer writes publish after audited commit. The publisher reads and locks its current audience, scene, affected layers and current object rows. Players receive no hidden object or layer metadata in the exercised races. Revoked, demoted, logged-out and expired sessions are checked before enqueue. Current visible revisions win over pending older ones. Tests also confirm a pending upsert cannot disclose an archived scene or reintroduce a deleted object. The private channel increment below applies the shared audience check to chat, hidden dice, initiative and additional token events.


## Private channel audit

Baseline `1fedb6f3af7585c27d599ceaefd682d9641661ee` used role lookups before chat/dice writes and relied on personal, GM or campaign rooms for content. Initiative could combine a tracker and entries from different commits, lacked scene scope and separated advance/stop writes from audit. Token owner delivery used the owner attached to the command result. These are confirmed code gaps. The post-fix regression exercises controlled interleavings and checks packets, current responses and storage.

- **Chat.** The write checks the session, non-archived campaign and both memberships inside one transaction. Players may send privately to Owner or GM. Managers may send to any member. Body and UUID validation and the existing 120 sends/minute/socket limit apply. Delivery checks current sender and recipient sessions and membership, including personal sockets outside the workspace. The ACK also requires its socket to remain joined. A current member can read their original threads after role change or the other party's departure. Loss of one's own membership blocks history until access is restored. Other managers cannot read it. The insert itself records authorship and recipient.
- **Dice.** The write checks current membership and role. Only Owner/GM can execute a hidden roll and only authorized managers receive its result, including the sending ACK. Public rolls still reach current campaign subscribers. The row records expression, result and detail. Chat history omits all rolls and the application has no REST dice-history route. Reconnect restores the campaign scope and live events. The roll list is transient.
- **Initiative.** Owner/GM mutations lock the campaign before changing the tracker and audit in the same commit. Readers lock scene and token state and use the same campaign gate as writers. The public projection omits hidden IDs, labels, scores and the current entry ID when hidden. The manager event requires the current manager role. Archive or activation invalidates the old tracked scene. The browser requests the current scoped snapshot and rejects late responses.
- **Token notes.** Current managers edit and assign under authorization, scene and token locks. The targeted event requires a current campaign subscriber, a live visible token on the active scene, the exact committed revision and current assignment. Managers retain both notes in their authorized full projection. Public token packets omit both notes. The former owner's client clears the old note on the sanitized reassignment packet. REST applies the same role, scene and ownership policy.

PostgreSQL cases cover pre-write revocation, post-commit demotion and removal, independent sessions, logout, expiry, supersession, archive and reconnect. Browser cases replay genuine frames and hold a real privileged HTTP snapshot over demotion. Revocation is enforced through synchronous enqueue. Already buffered/received data and user copies remain beyond recall. Append-only submissions have no command ID, so a permitted retry can create another row. The web client deduplicates repeated delivery of the same stored ID. [Regression entry point](../../apps/server/scripts/private-channels.mjs) · [Closure plan](../releases/V0.1.1_CLOSURE_PLAN.md)
