# Command retry and safe recovery policy

**Status: AUTOMATED_TESTS_PASSED.** A transaction can commit before an HTTP response or Socket.IO ACK reaches the client. The implementation supports replay for the commands below. See the [acceptance report](../releases/V0.1.1_ACCEPTANCE_REPORT.md) for executed checks and open coverage.

## Chat and dice request contracts

- IDs are UUIDs generated when the user begins an intention. A deliberate second identical message or roll gets a new UUID.
- Chat identity is `(campaignId, authenticated senderId, clientMessageId)`. Dice identity is `(campaignId, authenticated userId, requestId)`. The IDs are not authorization credentials.
- The request digest covers only operation payload fields that change the result: chat body and recipient; dice expression and hidden flag. Campaign/user scope comes from the authenticated command. Transport fields are excluded.
- The database row and result are committed together. Unique constraints serialize duplicate identities; dice also serializes same-key contenders before generating the persisted roll.
- A matching replay returns the stored row/result without a second audit row or event publication. A different digest returns `CONFLICT`.
- Session, campaign membership, role, recipient policy and current hidden-roll visibility are checked on every replay before the result can be returned.
- There is no time-based expiry for these two keys: they live exactly as long as their underlying message/roll row, currently until campaign deletion. Deleting a campaign cascades the rows and ends the guarantee. This does not create a separate unbounded receipt table.
- A transaction rollback leaves no key reservation, so the same ID can be retried. Network delivery itself remains best-effort.

## Client recovery behavior

Chat and dice keep one pending operation in component memory. After five seconds without an ACK, the next explicit click retries the same ID and payload. REST creates, copies and uploads use in-memory keys indexed by method, path and payload. The UI shows an unknown outcome after a lost or invalid response or a server error. The same action reuses its key. A changed input or a new action after success uses a new key. The Add token button retains its original derived name and position across realtime updates. Changing user, campaign or role clears all keys. Changing the active scene clears scene keys while preserving campaign operations, including an in-flight first scene create. Tabs and page reloads have separate memory.

Resource adjustment reloads the authorized token snapshot after an unconfirmed response. A write with the stale version conflicts. Adjustments are one point per command. In the browser test the fifth decrement from 20 HP commits at 15, the response drops and the old version receives HTTP 409. The snapshot shows current HP and cannot identify which command caused it.

The asset library holds the batch key after HTTP 207 and refreshes displayed assets from the server to avoid duplicate cards on replay. Upload Map also protects the file upload stage with a receipt. Attaching that asset to the scene is a separate versioned write.

## Retention and limits

REST uses the optional `Idempotency-Key` UUID header. An invalid UUID returns HTTP 400. PostgreSQL serializes the same identity with an advisory lock and a unique constraint. The canonical SHA-256 digest holds no original payload. The transaction stores the receipt and result IDs together with the relevant domain records. Same-key changed content returns HTTP 409 `CONFLICT`. Current authentication and role checks can deny replay. An unavailable result can return HTTP 409 `RESULT_UNAVAILABLE` or an access or source error.

REST receipts expire after 90 days using the PostgreSQL clock. A repeat after expiry can create a new result. Deletion of the owning actor or scoped campaign cascades its receipts. Actor-scoped campaign creation retains its receipt independently of the created campaign. The prune command deletes expired rows in bounded batches and skips locked rows. A subsequent daily run can pick up skipped rows. A parallel live replay retains its result. See the [operations handoff](../operations/PERF_GPU_OPS_HANDOFF.md) for scheduling on the selected host. Chat and dice keep their IDs with their own rows.
