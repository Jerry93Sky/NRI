## Ручная приёмка владельцем

**QA-OWNER · MANUAL_ACCEPTANCE_PENDING · P1 · M.** Пока имеется автоматизация отдельных операций и изолированные технические прогоны. Влияние — пригодность стола для полной игры на согласованном оборудовании. До V0.1.1 владелец и независимые участники проводят 30–60 минут в демо-копии **Amber Crossing: The Lantern Vault** на точном SHA. Используют Owner/GM и двух Players в отдельных браузерах или на разных устройствах.

1. Открыть карту, откалибровать сетку, проверить указатель, рисование, перенос токенов и объектов, undo/redo и конфликт двух клиентов.
2. Проверить скрытую сцену и слои, публичный и приватный чат, открытые и скрытые броски, начало/ход/раунд/стоп инициативы. Демоция, смена владельца токена и удаление участника должны очищать прежние права и UI. Проверить переподключение и поздние события в продолжающейся сессии.
3. Сверить пригодность панели и Canvas на согласованных разрешениях, затем перезапустить API и подтвердить восстановление кампании и последнего состояния. После технического прогона проверить результат восстановления из резервной копии.
4. Записать SHA, окружение, роли, результат каждого пункта, артефакты и принятые владельцем решения по остаточным дефектам. Этап зависит от технических пунктов выше и переносится только вместе с релизом. [Сценарий приёмки](V0.1.1_MANUAL_ACCEPTANCE.md)

## Конечный scope RT-RETRY

**Статус следующей задачи: `PLANNED`; реализация не входит в CMD-ACL.** Под “потерянным ответом” понимается commit на сервере, после которого HTTP response или Socket.IO ACK не дошёл до клиента. Текущий клиент не делает автоматический retry для строк ниже; повтор пользователем считается новым запросом, если серверная команда не имеет отдельного dedupe predicate.

| Путь | Commit без ACK и повтор | Как узнать результат сейчас | Минимальная следующая мера |
| --- | --- | --- | --- |
| Public/private chat | Сообщение остаётся append-only; ручной повтор создаёт новое сообщение | История возвращает последнее разрешённое состояние, но неоднозначный текст придётся распознать | Принимать один устойчивый `clientMessageId` на участника; дедуплицировать запись и возвращать исходный ID |
| Dice roll | Бросок записан; ручной повтор выполняет новый случайный бросок | Истории бросков нет, долговечного recovery нет | Ограниченный roll request ID с сохранённым результатом и повторным ACK; решение о периоде хранения входит в задачу |
| Token create | Токен уже существует; повтор создаёт ещё один | Scene snapshot покажет созданную сущность, но не отличит retry от намеренного второго токена | Использовать ограниченный request ID; snapshot достаточно для ручного восстановления |
| Token duplicate / group copy | Копии уже существуют; повтор создаёт новые копии | Scene snapshot показывает новые ID; невозможно определить, какая группа соответствует потерянному ACK | Один request ID на batch duplicate, связанный с requester/campaign и исходным payload digest |
| Resource adjustment | Изменение сохраняется; повтор со старой версией отклоняется как stale | Текущий token snapshot/version выявляет факт изменения, хотя не автора действия | Сначала reload/сверка версии; отдельный idempotency key обычно не нужен, если UI показывает конфликт и текущее значение |
| Scene create | Сцена сохраняется; повтор создаёт ещё одну | Авторизованный список сцен показывает обе | Request ID для create, чтобы безопасно повторить после явного неопределённого исхода |
| Scene duplicate | Копия сохраняется; повтор создаёт следующую копию | Список сцен показывает обе копии, но нет связи с запросом | Request ID на copy с digest источника/версии |
| Campaign create | Кампания и Owner membership сохраняются; повтор создаёт другую кампанию | Campaign list показывает запись, но нет связи с запросом | Request ID на create, возвращающий сохранённый campaign ID |
| Campaign duplicate | Копия и файлы могут быть committed; повтор создаёт ещё одну независимую копию | Campaign list показывает результат; для больших копий момент ответа неочевиден | Request ID на copy; включить результат компенсации файлов в контракт |
| Asset upload | Asset metadata and files commit; повтор загружает второй asset | Campaign asset library показывает новый файл, но не связывает его с потерянным ответом | Upload request ID плюс сохранённый asset ID; сначала сверка library, повтор только с тем же ID |

**Предлагаемая граница RT-RETRY:** начать с устойчивых IDs для chat и dice (где текущие version/snapshot механизмы не позволяют восстановить исходный результат), затем покрыть duplicate/upload/create endpoints, создающие новые сущности. Для resource adjustment сначала использовать уже имеющийся version conflict и авторизованный snapshot. Не строить универсальный command framework, durable queue или replay bus; согласовать scope по этим тестам потери ответа до реализации.

**FUTURE-DELIVERY · PLANNED · P3 · L.** Общий протокол command IDs, event cursors и переживающая перезапуск очередь имеют смысл при доказанной потребности в повторе за пределами штатного reconnect. Они не нужны для закрытия критериев, если RT-RETRY пройден. До переноса остаются версии, транзакции и авторизованные снимки. Зависимость — принятый сценарий восстановления и измеренная эксплуатационная потребность.
